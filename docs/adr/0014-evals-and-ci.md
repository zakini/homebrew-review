# 14. Evals and CI

Date: 2026-10-09

Status: Accepted

## Context

The tests prove the code works but not that the model's verdicts are good. Checking that needs the real API, which costs money, so it shouldn't run on every change. Checks should run on pull requests without exposing the API key to code from forks.

## Decision

### Evals

- **Labelled cases**, each a saved `Signals` JSON file and the expected verdict, are fed to `judge` and scored against the real model. Signals can be generated by running the real signal-gathering code over a small fake home directory, or captured in the macOS test VM ([ADR 15](0015-macos-test-vm.md)), then saved.
- **The unit tests validate every saved case against the `Signals` schema**, so cases fail loudly rather than going stale when the shape changes.
- **Weight wrongly calling an in-use package "probably unused" far more heavily** than other mistakes, since that's the error that leads to removing something the user needs.
- The cases themselves aren't decided here; the user will review them once they're added.

### CI: GitHub Actions on pull requests only

Alongside the tap's existing `brew test-bot` workflows, and only `on: pull_request`, so pushes don't trigger runs.

- **Checks workflow:** `npm ci`, then typecheck, lint and tests. Take the Node version from `.node-version` (`actions/setup-node`'s `node-version-file`). `.npmrc`'s `ignore-scripts` applies to `npm ci` too.
- **Evals workflow:** required to pass before merging, but only runs when the user approves it.
  - Keep the prompt, the model ID, `judge` (including how it turns signals into the prompt), the `Signals` schema, the eval cases and the eval runner in their own files (e.g. `src/judge/**`, and `evals/**` for the cases and runner) so changes to them can be detected. Signal gathering doesn't affect the evals, which use saved signals.
  - **A `detect` job** runs on every PR and outputs whether those files changed (`git diff` against the base branch).
  - **An `evals` job** with `if: needs.detect.outputs.changed == 'true'` and `environment: evals`. The `evals` environment has the user as a required reviewer, so the job waits ("Review deployments") until approved, and its check stays pending until then. When nothing relevant changed, the job is skipped, and GitHub counts a skipped job as passing a required check.
  - **Make the `evals` job a required check**, with a `concurrency` group so a new push cancels older runs still waiting for approval.
  - **Store `ANTHROPIC_API_KEY` as an `evals` environment secret**, not a repository secret, so only approved runs can read it. The eval runner builds the model from it and passes it to `judge`, as tests pass mock models. It never goes through the CLI's stored-key loading.
  - Environment required reviewers need a public repo on free plans. Homebrew taps are public, so this is fine.
- **Never use `pull_request_target`.** `pull_request` withholds secrets from fork PRs, which stops someone's PR code reading the API key. `pull_request_target` would give the key to their code.
- **Pin third-party actions to a commit SHA** rather than a tag.

## Consequences

- Every PR that touches the judging side waits for the user's approval before it can merge.
- The checks workflow comes with the CLI and config task; the evals workflow comes with the review process.

## Alternatives considered

- **A `paths` filter on the evals workflow:** a required check from a workflow that never runs stays "Expected — Waiting for status to be reported" and blocks every PR that doesn't touch those files.
- **Running evals when signal gathering changes:** the evals use saved signals, so those changes don't affect them.
